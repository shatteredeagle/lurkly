# Twitch playback + chat in Tauri 2 (Linux/WebKitGTK) - research 2026-10-27
Confidence note: web search was shallow; items marked (unverified) come from memory/forum posts and need a 10-minute spike.

## Recommendation
- Video: Twitch official embed (JS `Twitch.Player` or iframe player.twitch.tv) loaded from a tiny LOCAL HTTP server (tauri-plugin-localhost, or axum in the Rust backend) so the page origin is http://localhost:PORT and `parent=localhost`. One shared WebView session logs in once (Twitch login inside the player/ a login window), giving sub/no-ads. Official, ToS-clean, no HLS/MSE plumbing.
- Chat: official embed (twitch.tv/embed/<chan>/chat?parent=localhost&darkpopout) for v1 (login = can send, sub emotes/badges work, zero maintenance). Custom IRC client only if "beautiful" theming is the priority; it is a v2 option.
- Multi-tab: one player instance, destroy/recreate iframe on tab switch (or keep max 1-2 alive). Mute others implicitly by destroying.
- Fallback if embed ads/login prove flaky: mpv/streamlink with --twitch-api-header Authorization=OAuth <token> (ToS-gray, see 1c).

## 1. Video
(a) Embed iframe / JS embed
- `parent` is mandatory for iframe embeds (one per hosting domain); for JS embed only needed when embedding on other domains. https://dev.twitch.tv/docs/embed/video-and-clips/
- localhost is accepted as parent, HTTPS not required for it; file:// pages are not supported; pass bare hostname with NO port (a port in parent gave 400). https://discuss.dev.twitch.tv/t/embed-parent-query-string-value-was-not-specified/27948 , https://discuss.dev.twitch.tv/t/twitch-embedded-player-updates-in-2020/23956
- Twitch staff: no parent value works for mobile webviews; parent is enforced (via frame-ancestors CSP / referrer-origin). https://discuss.dev.twitch.tv/t/how-will-twitch-embed-updates-affect-mobile-app-embeds/26008
- Tauri origins: Linux/macOS prod = tauri://localhost, Windows/Android = http://tauri.localhost. A custom scheme is not a valid parent (unverified for Tauri specifically; no Tauri+Twitch writeups found). tauri.localhost as parent would only apply on Windows. So on Linux: serve the player page from http://localhost:PORT (tauri-plugin-localhost https://v2.tauri.app/plugin/localhost/ ) and either point a child webview at it or iframe it. The top-level Tauri page need not be the Twitch-embedding page; the *immediate* embedding page's host is what counts (ancestor chain is checked, so a tauri:// page iframing http://localhost page that iframes Twitch may fail: make the localhost page top-level in a child webview, or just load the whole UI from localhost).
- Workarounds seen in Electron: strip CSP/frame-ancestors via onHeadersReceived (mixed reports). Not needed with localhost.
- Login/ads: Twitch staff say a logged-in viewer's session and sub benefits apply in embeds; if no ads on twitch.tv, same in embed. https://discuss.dev.twitch.com/t/an-updated-twitch-embedded-player-viewer-experience/41718 . Needs third-party cookies for player.twitch.tv: WebKitGTK default cookie policy may block third-party cookies (ITP); set cookie accept policy ALWAYS (webkit2gtk CookieManager::set_accept_policy) (unverified default) and persist cookies to a file (tauri/wry data dir persists by default). Login: open https://www.twitch.tv/login in a window using the SAME webview data store; then embed sees the session. Twitch login may show captcha/block webview UAs: test; set a normal Firefox UA string. Aggressive tracker blocking caused sub ads for a Brave user. https://community.brave.com/t/twitch-pre-rolls-bypass-shields-even-for-subscribed-users-that-arent-supposed-to-see-ads/300660
- Logged-out embeds show ads / purple "login to watch" prompts (hence login matters).

(b) Full site / popout in a child webview
- https://www.twitch.tv/popout/<chan>/chat and the full site work as top-level pages (no parent check), cookies persist, login once, sub no-ads for sure. Cons: heavy (full React app), can't hide site chrome without injected CSS/JS (initialization_script + CSS to hide nav; fragile). Player-only popout (twitch.tv/<chan> with injected CSS) is the most reliable ads-free path but brittle on UI changes. Tauri 2 child webviews = `unstable` feature (WebviewBuilder, window.add_child) - works on Linux but layout is manual and has Wayland/GTK quirks (unverified).

(c) Native HLS (usher.ttvnw.net + GQL PlaybackAccessToken)
- GQL (gql.twitch.tv/gql, public web Client-ID) PlaybackAccessToken -> usher m3u8 with Authorization: OAuth <auth-token cookie>. Sub/Turbo token avoids ads (streamlink docs: --twitch-api-header). Streamlink issue: Twitch started embedding ads in HLS for non-authenticated tokens; workarounds repeatedly broke. https://github.com/streamlink/streamlink/issues/4949
- Auth-token extraction from cookie is against ToS-ish spirit (unofficial API, Client-ID spoofing); account risk low but real; Twitch changes break it. Streamlink pypi warns of ad-bypass legality.
- WebKitGTK: MSE exists but is runtime-setting + GStreamer-dependent; codec/HW decode variable on Linux. hls.js in WebKitGTK: it can use native HLS (WebKit GStreamer supports HLS via playbin) or MSE; reliability varies by distro GStreamer plugins (needs gst-libav / gst-plugins-bad). https://blogs.gnome.org/mcatanzaro/category/gnome/page/4 (old; recheck). Safer: spawn mpv/streamlink as separate window (not embedded in webview; embedding via --wid is X11 only, bad on Wayland).
- Latency: low-latency HLS ~2-5s via mpv/streamlink --twitch-low-latency; embed ~3-6s. Ads: sub => none, but a non-sub channel on the same token => pre-roll in HLS stream.
- Pros: lightweight, quality control, no cookies. Cons: ToS risk, breakage, MSE/codec risk in webview, can't play in-webview reliably, sub perks (e.g. badges) irrelevant. Not recommended as primary.

## 2. Chat
(a) Official embed: https://www.twitch.tv/embed/<chan>/chat?parent=localhost ; add `&darkpopout` for dark theme (documented on Twitch's popout/embed examples; the dev doc page doesn't list it - unverified). https://dev.twitch.tv/docs/embed/chat/ . Logged-in via same cookie jar => can send messages, sub emotes/badges/ BTTV not (unless user has BTTV extension - no). Theming: only dark/light, no CSS access from iframe (cross-origin). No 7TV emotes. Looks like stock Twitch chat.
(b) Custom client: connect wss://irc-ws.chat.twitch.tv:443 , `CAP REQ :twitch.tv/tags twitch.tv/commands`, PASS SCHMOOPIIE, NICK justinfan12345, JOIN #chan; reply PONG to PING. Parse tags: badges, color, display-name, emotes (id:start-end), emote-only, reply-parent-*, room-id, first-msg. https://discuss.dev.twitch.tv/t/anonymous-connection-to-twitch-chat/20392 . Emote images: https://static-cdn.jtvnw.net/emoticons/v2/<id>/default/dark/2.0 . Badges: Helix GET /chat/badges/global and /chat/badges?broadcaster_id= (needs app access token, i.e. registering a Twitch app + client secret) or unofficial GQL. Third-party: 7TV https://7tv.io/v3/emote-sets/global and /v3/users/twitch/<id>; BTTV https://api.betterttv.net/3/cached/emotes/global and /users/twitch/<id>; FFZ https://api.frankerfacez.com/v1/room/id/<id> (all from memory; verify). Rust crate `twitch-irc` or just do it in JS. Effort: ~2-4 days for polished (virtualized list, replies, badges, emotes, cheers, bits, slash-me, mentions, scroll-lock). Sub emotes from other channels render fine since the ids come in tags.
- Sending needs a user OAuth token with chat:edit (+chat:read), via Device Code flow / implicit grant with own registered Twitch app (https://dev.twitch.tv/docs/authentication/) , IRC PASS oauth:<token>, or Helix POST /chat/messages with user:write:chat. Needs the app registration; can't reuse the cookie session.
(c) For minimal+beautiful: custom wins on theming (fonts, density, transparency, hidden toolbars); official wins on effort and "sub perks work". Chat is optional per tab, so ship embed first, custom read-only later.

## 3. Multi-tab
- Keep exactly one live player: on tab switch destroy the iframe (about:blank) and recreate (cost ~1-2s reconnect). Optionally keep previous alive N seconds. Hidden iframes still decode/stream.
- Pause via Twitch.Player API: player.pause()/setMuted(); but Twitch embed also throttles hidden players only partly; destroy is the sure way.
- Audio: mute-by-destroy; JS API setVolume/setMuted; WebKitGTK allows autoplay with a user gesture on the app (autoplay may need `webkit` setting media-playback-requires-user-gesture=false in wry: use `WebviewBuilder::with_...` / env not trivial - verify).
- Quality: JS embed: player.getQualities() / setQuality('chunked'|'720p60'...). Iframe embed has no control; user uses gear menu. Auto-ABR default is fine. Per-tab quality preference only possible via JS API (call after READY event).
- Use Helix GET /streams/followed or GQL for live-channel list (follows scope user:read:follows), poll 60s.

## 4. Tauri 2 window gotchas (KDE Plasma/Wayland)
- decorations:false: on Wayland, drag via `data-tauri-drag-region` or window.startDragging(); resize handles don't exist -> use window.startResizeDragging(direction) with invisible edge divs (needs core:window:allow-start-dragging / allow-start-resize-dragging capabilities). tao 0.30.3 fixed Wayland header drag and border resize + maximize protocol error 71: ensure tauri >= 2.1 / tao >= 0.30.3. https://v2.tauri.app/release/tao/v0.30.3
- Custom titlebar buttons need capabilities core:window:allow-minimize/maximize/close/toggle-maximize. A real-world workaround: decorations:false + transparent:true custom React titlebar; GTK CSD buttons unreliable on KDE/Wayland. (openless PR #531)
- Shadow/rounded corners: transparent window needs macOSPrivateApi on mac only; on Linux compositing OK, but WebKitGTK transparent bg may need WEBKIT_DISABLE_COMPOSITING_MODE or DMABUF quirks; common env workaround: WEBKIT_DISABLE_DMABUF_RENDERER=1 if blank/flicker (NVIDIA).
- always-on-top: set_always_on_top works on X11; on Wayland the protocol has no always-on-top, KDE only honors it through KWin rule or XWayland (run with GDK_BACKEND=x11 for it to work) (from memory; verify). Same for programmatic positioning.
- PiP: no native PiP in WebKitGTK; Twitch's own PiP button likely absent. Do your own: second small frameless always-on-top window (KDE user adds a KWin "keep above" rule) loading same localhost player URL; or `<video>.requestPictureInPicture()` unsupported in WebKitGTK (verify).
- Autoplay + WebKitGTK media: need gst-plugins-good/bad/libav installed; hardware decode via VA-API gstreamer-vaapi optional.
- Child webviews need `unstable` feature; avoid if possible.
